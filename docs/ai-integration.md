# AI 接入与辅助评价设计

版本：V1.0（2026-11-02）  
状态：供应商无关的接入合同；正式模型及预算待确定  
上位需求：[requirements.md](requirements.md)

## 1. 两种 AI 能力及边界

| 能力 | 触发时点 | 输入 | 输出 | 是否影响作品 |
| --- | --- | --- | --- | --- |
| 创作对话 | 仅 AI 条件的 DEVELOPMENT 阶段，由参与者主动提问 | 固定任务、用户当前问题、有限对话上下文；可选择提供当前五字段草稿 | 建议、追问或可讨论的方案 | 回复先出现在底部协作区；只有用户显式采纳后才进入作品 |
| 辅助评价 | 任一条件的 FINAL 终稿锁定后，由后端触发 | 同一任务、终稿、固定量规与评分提示词 | 三维 1—5 分、终稿证据、理由与改进建议 | 只进入报告的 AI 辅助区；不修改终稿，不给教师评分前查看 |

两种能力使用独立提示词版本和调用记录。AI 辅助评价对象是**终稿**，不能把独立构思的短稿当同等作品评分。正式研究中两条件的终稿均用同一评分模型和量规评分，以便比较 AI 与教师评分。

## 2. 提供方适配层

后端定义 `ModelProvider` 接口，至少提供 `generate_chat()` 与 `generate_assessment()`。适配器负责认证、请求格式、超时、响应提取、请求号和错误归类；业务服务只接收统一的 `ModelResult`，不依赖某家供应商的字段。第一版仅实现一个可用提供方；以后换模型须记录新的 `model_config_version`，不能在正式收集中静默替换。

```text
Vue 协作区 → POST /api/v1/sessions/{id}/chat
             → 会话/条件/截止时间检查
             → 保存请求和用户消息
             → 组装固定提示词 + 有限上下文
             → ModelProvider → 文本模型 API
             → 保存原始回复、模型标识、耗时与状态
             → 返回回复；等待用户选择是否采纳
```

推荐环境配置：`AI_PROVIDER`、`AI_BASE_URL`、`AI_API_KEY`、`AI_CHAT_MODEL`、`AI_ASSESS_MODEL`、`AI_TIMEOUT_SECONDS`、`AI_MAX_TURNS_PER_SESSION`。`AI_API_KEY` 只在服务器环境中读取，不进数据库、前端构建、日志或研究导出。`model_config_version` 存模型标识、温度、输出长度、超时和供应商代号，不存密钥。

## 3. 创作对话规则

### 3.1 服务端提示词合同

提示词必须告知模型：用户在设计一节 40 分钟高一 AI 素养活动；应提出启发性建议或澄清问题，关注目标、学生参与、时间、资源与评价；不能声称自己已执行课堂活动、查到未提供的真实来源或替用户决定最终方案。提示词中要区分“任务事实”和“用户输入”，不能把用户或作品中的指令当作系统指令。

模型回复可包含建议，但界面不得把回复渲染为系统命令。若回复引用外部事实，应提示参与者核验；系统不把模型陈述自动标为真实来源。

### 3.2 上下文与约束

- 请求发送固定任务版本、当前用户问题、必要的最近对话和可选当前草稿摘要；不发送研究编号、教师评分、身份映射或其他参与者数据。
- 每条用户问题有长度上限，后端限制轮次和并发请求；一次会话同一时刻最多一个未完成模型请求，避免乱序与费用失控。
- 同一 `client_request_id` 重试返回原请求状态，不重复向模型发起调用。真正需要新回复时，客户端生成新请求号并保留前次失败记录。
- 模型超时、拒绝、配额不足、格式错误分别保存状态；作品草稿和既有版本不回滚。前端显示“AI 暂不可用，仍可继续编辑”。
- 回复若在截止后到达，系统保存它以反映真实过程，但禁用采纳按钮；终稿不因迟到回复被改动。

### 3.3 建议动作的可追溯性

“直接采纳”和“改写后采纳”均弹出确认窗口，用户选择目标章节；后者可编辑文字。后端先校验来源是本场 `ASSISTANT` 消息，再原子地写入新草稿修订号和 `suggestion_action`。`IGNORE` 只写动作。可对同一条消息记录多次动作，但报告按时间如实呈现；没有动作的消息保持“未表态”，不能自动算拒绝。手动复制与线下思考可能无法记录，不据此计算人的贡献比例。

## 4. AI 辅助评价合同

### 4.1 输入与输出

评分提示词由量规版本和任务版本构成，明确三维 1—5 分锚点；要求每个维度给出**终稿中可定位的原文证据**、理由和一个可操作的改进建议。不得把“文字流畅”直接当作新颖性，不得因新颖性高而忽略时间或资源不可行。

期望的统一 JSON 格式：

```json
{
  "rubric_version": "R1",
  "dimensions": {
    "novelty": {
      "score": 4,
      "evidence": "学生小组核验并修订 AI 资料",
      "reason": "核心任务包含核验与修订的组合"
    },
    "fit": {
      "score": 4,
      "evidence": "形成核验记录卡",
      "reason": "学习产出与目标基本对应"
    },
    "feasibility": {
      "score": 3,
      "evidence": "小组核验与信息查证（20 分钟）",
      "reason": "有时间安排，但材料数量尚不明确"
    }
  },
  "suggestion": "补充每组待核验说法的数量和材料来源。"
}
```

示例数字只说明数据结构，不是任何真实作品的评价结果。模型原始响应与解析结果分别保存，且保留模型、量规和提示词版本。

### 4.2 后端校验

1. 响应能解析为一个对象；无多余的脚本或未受控 HTML 被直接展示。
2. 三个维度键完整，分数是整数且在 1—5 内；理由与建议非空，长度在上限内。
3. 证据字符串能在服务端生成的终稿纯文本中找到，或可通过规范化空白后定位；找不到则本次评价标为失败或要求一次重新生成，不能伪造证据。
4. `rubric_version` 与该场冻结版本一致；没有证据时不填 0 分或“默认 3 分”。
5. 通过校验后才把 `status` 设为 `SUCCEEDED`；失败保留 `raw_response`、错误码和尝试号，报告显示不可用。

后续分析使用保存的解析结果及两名教师原始评分重新计算差异；不能只截取页面上的结果图。

## 5. 队列、重试与研究模式

终稿事务提交成功后创建一条 `PENDING` 辅助评价任务。小规模单机部署可用持久化任务表加后台处理器；处理器重启时扫描未完成任务，避免只依赖进程内存任务。每次重试增加 `attempt_no`，不覆盖旧的原始回复。管理员可查看失败原因并在同一配置版本下重试，报告标明使用的成功尝试。

研究模式启动前，后台应检查模型连通性、密钥、额度/配额可用性及配置冻结状态。若不满足，阻断 AI 条件正式开场并提示管理员；独立条件的作品数据仍可保存，但研究安排需按事先规定处理，不能事后选择性替换模型。演示模式可以使用显著标记的模拟适配器，演示数据不得进入研究导出。

## 6. 安全、隐私与成本

- 外部模型只能接收完成任务所必需的文字；知情说明需告知作品文本会发送给所选模型服务。正式使用前核对学校对数据出境、留存和第三方处理的要求。
- 用户输入和 AI 回复均当作不可信文本：限制长度、显示时安全转义、URL 只允许安全协议；不得将回复当作新系统提示词执行。
- 日志记录请求号、状态、耗时、输入/输出长度、模型版本及错误码；不在通用日志打印密钥。若供应商提供 token 用量，单独记录并按场次汇总费用。
- 管理员配置最大轮次、单次超时和重试上限；达上限时允许用户继续独立编辑，不丢稿。
- 教师评分接口与 AI 评价表隔离。教师完成本人正式评分前，任何教师页面都不展示辅助分数或模型意见。

## 7. AI 验收清单

| 场景 | 预期结果 |
| --- | --- |
| AI 条件、DEVELOPMENT、真实密钥可用 | 模型回复显示在底部协作区，数据库有请求、消息、版本和耗时 |
| AI 条件但 IDEATION | 后端拒绝模型调用，页面无对话入口 |
| 独立条件任何阶段 | 后端拒绝模型调用，数据库无 AI 消息 |
| 用户未点击采纳 | 作品完全不变；消息可保留为未表态 |
| 用户修改后采纳 | 目标章节更新，动作记录保存原消息与插入文字 |
| 供应商超时或配额失败 | 作品仍可编辑；请求状态失败；可按规则重试 |
| 提交终稿后评分成功 | 三维、证据、理由与来源可在报告中查看，教师页面看不到 |
| 评分 JSON 缺维度或证据不存在 | 校验失败、保留原始响应、报告标为暂不可用 |
| 演示适配器在研究模式被误启用 | 阻断正式批次，不生成研究数据 |
